## Freshness and latency

Each resolution captures distinct active sources before its first await. All source identities are read in parallel, the epoch is observed, and all source identities are rechecked before a cache hit can return. A miss reads primary placement and rechecks identities; old-method fallback also rechecks. Proof-header and secondary placement reads, when enabled, run in parallel followed by one final identity recheck. Proof verification/placement comparison/cache insertion/publication are synchronous after that check. Transport or shape failures never fall back to an old cached identity.

For a stable ordinary cache hit this costs two primary identity RPCs plus the existing epoch RPC (three dependent rounds). A plain miss adds a primary placement RPC and one fresh identity RPC (five rounds). Proof and/or secondary adds their parallel data round and a parallel identity round (seven rounds total). Distinct active sources receive one identity read per checkpoint, and identical `RpcSend` function references are deduplicated. There is no retry loop. These checks intentionally prioritize observed identity over the prior one-epoch cache latency; they do not create a cryptographic proof of network identity.

## Residual risks

`eth_chainId` is the existing node-asserted identity, so intentionally equal chain IDs, dishonest identity replies, and switch-away-and-back events between observations remain indistinguishable. Every primary identity actually observed by a selected-alias resolver must match that selection, including a foreign-chain resolver interval between two selected-chain metadata/final checks. Cached answers still inherit the existing same-network sealed-epoch trust/proof policy; endpoint authenticity, current-route/private-channel readiness and signed-read network domains remain their existing separate checks. This change does not make legacy CAP1 a private-placement capability or make an ingress private transport confidential. Failed calls retain no new answer; already accepted older cache entries can be reused only after fresh matching chain/epoch observations. Broader restart/load/host-loss behavior is outside this in-memory client-local repair.
