# Digest-key rotation preparation (PLACE-03)

The offline `buildDdbDigestRotationPreview` and `buildDdbDigestRotation` helpers prepare operation10 for a caller signature. They do not import keys, call a node, authorize a recovery window or activate a migration. Both use operation preimage v2 and require the intended chain ID. They are exported from the Node, browser and React Native entrypoints.

```ts
const previewRequest = buildDdbDigestRotationPreview({
  contract, from, callerPubKey, toFingerprint,
}, { chainId, preimageVersion: 2 });
// Sign previewRequest.hash with the owner's/admin's ML-DSA-87 key.
// Send its signed envelope directly to ddb_previewDigestRotation.

const migration = buildDdbDigestRotation({
  contract, from, callerPubKey,
  payload: returnedDataHex,
  expected: {
    fromVersion, fromFingerprint, toFingerprint,
    placementVersion, expectedPrior, asOfBlock,
  },
}, { chainId, preimageVersion: 2 });
// Sign migration.hash as a NEW operation and submit its signed envelope.
```

The preparation request's exact Data is `{"to_fingerprint":"0x<64 lowercase hex digits>"}`. The next fingerprint identifies an already provisioned digest key; no secret key belongs in this request. The selected placement host requires owner/admin authority, active features, the governed recovery window and access to the necessary keys. It scans one bounded snapshot without writing or changing the active key and returns the exact full migration Data as hex.

Retain `expected` independently from trusted finalized chain state and the locally intended next key. Do not fill it by copying an unverified host's returned fields. It binds the old version and fingerprint, intended new fingerprint, placement version, prior anchor and finalized snapshot block. If the preview races a new finalized block or placement/key change, refresh the trusted state and preview again; do not relax the comparison to make a stale proposal pass. Use `bigint` for versions and block numbers above JavaScript's safe integer range.

The final helper accepts exact payload bytes or lowercase RPC hex. It checks canonical JSON field names/order, exactly2048 target-lane bytes, uint64 bounds, consecutive versions and every expected binding before preparing the signature. Version0 requires a zero old fingerprint and advances to1; later rotations require a nonzero old fingerprint. The new fingerprint must be nonzero and distinct. Version18446744073709551615 cannot advance. Whitespace, duplicates, unknown or reordered fields, aliases, malformed encodings and oversized inputs refuse. Payload integers never pass through `JSON.parse`, and the returned envelope contains the original accepted bytes.

The builder verifies the public bindings and byte representation. It cannot prove that the target lanes correspond to a truthful SQL scan. The placement group independently checks the migration, and finalized admission enforces the governed window, current state, placement and freshness. Preview success is not activation. Keep old keys and historical bindings required for recovery; an encryption-key change does not itself rotate row-digest tags. Wait for the admitted migration and local application before using its new digest version.

Both helpers return the ordinary `DdbPreparedOp`: `hash`, `requestId` and `envelope`, with numeric type10. Shared signing options validate nonce, timestamp, gas limit, expiry and signing-key version. A fresh nonce is generated by default for each preparation; the final migration is a distinct signed request from its preview. Other reserved operation types remain refused by the shared v2 codec. Ordinary `buildDdbOp` behavior is unchanged.
